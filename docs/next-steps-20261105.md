## 1. 建议的主线

接下来的一个月，围绕一个研究问题和一个真实应用推进：

- 研究问题：**在有界开销下，如何利用证据缺口、专家材料互补性和新增证据决定协作动作，使协作更有效？**

建议先做基线核对和开发集诊断，再做最小机制实验；应用资料收集同时进行。多智能体优于单智能体是要检验的假设，实验也允许得到不支持该假设的结果。导师关于论文结论的疑问，应通过复现条件核查来回答。

当前最主要的能力缺口：

1. **中文检索及跨跳实体处理。** `bm25_retriever.py` 的 tokenizer 只识别 `[a-z0-9]+`。`corpus.py` 明确拒绝没有英文/数字正文词项的材料；中文夹数字的材料即使能入库，也不代表具备中文语义召回。`src/agents/retriever.py` 的跨跳实体抽取同样依赖英文首字母大写模式。
2. **中文长答案与流程答案评价。** `src/evaluation/metrics.py` 使用 HotpotQA 英文归一化和空白分词；现有 `JobRequest.primary_metric` 也固定为六项 HotpotQA 指标。中文条款、条件和材料清单需要另外设计评价。
3. **论文方法对应关系。** `experiment_methods.py` 将六个方法名映射到平台模板。代码中的名称及本次所查文档，尚不能证明这些模板逐项复现了某篇具体论文。
4. **可移交的运行服务。** 稳定非流式问答合同、独立系统包、异机导入运行和部署说明仍有缺口。现有 API 是可复用基础，部署工作应围绕它继续完成。
5. **通用业务执行。** 当前角色、状态与路由围绕问题、证据、审核设计。真实订单执行还需要结构化业务输入输出、工具注册、外部动作权限、幂等及失败恢复。

## 3. 研究线：先回答“当前比较究竟说明了什么”

### 3.1 已有结果的准确起点

既有 `docs/evaluation-analysis-20261029/evaluation-analysis.md` 汇总了 1,000 道保留评价题、六种方法、6,000 项首次尝试。以下 F1 使用 0—100 尺度：

| 方法 | Answer F1 | 平均模型调用 |
| --- | ---: | ---: |
| 单智能体 RAG | 55.96 | 1.046 |
| 固定流水线 | 60.11 | 1.999 |
| 自适应流水线 | 60.68 | 2.829 |
| 多专家 | 54.39 | 3.998 |
| Lead | 45.44 | 5.363 |
| Debate | 35.33 | 10.417 |

因此，当前问题可以收敛为：为什么规划与证据获取有帮助，而更复杂的协作没有转化为额外收益？

- 自适应减固定的 F1 差值约 +0.56，按题 bootstrap 95% 区间为 [-0.88, +1.97]，调用约多 41.5%。尚无清晰证据证明自适应优于固定，也不能据此判定二者等效。
- 自适应的平均支持事实覆盖从 73.69% 到 74.40%，增加约 0.71 个百分点。
- Debate 的初始和累计支持事实覆盖均为 53.93%，997 项带有后续检索无新增证据的轨迹标签；这提供研究线索，不能单独证明根因。
- Debate 即使将 51 项失败全部假设为 F1 满分，均值上限也只有 40.43，仍低于固定流水线。修复执行失败之外，还要检查已完成但答错或弃答的过程。

这些都是旧实验的观察。进一步调参应使用开发材料；原报告和首次成绩继续保留。

### 3.2 第一项交付：论文—实现对应表

先选择一篇协作方法和一个强单智能体方法做核对，控制工作量：

- 协作候选：Du 等的 Multiagent Debate（ICML 2024），有作者代码；先核查原论文的输入、数据集、提示词、轮数、专家可见信息和最终答案读取方式。
- 单智能体候选：IRCoT（ACL 2023），适合核对多步检索与推理。其原始语料与检索设置需单独核查，不能直接拿论文分数对比当前逐题 distractor context。

对应表逐项记录：论文主张、论文/代码位置、平台实现位置、差异、差异可能影响、可运行复现条件。优先检查：

1. 原论文是否使用相同模型或模型能力档位、相同数据任务和上下文设置。
2. 原方法能否主动改写查询或获得新证据，平台是否只重复检索相似内容。
3. 论文最终取多数票、某个专家答案还是单独审核，平台严格引用与弃答规则是否改变任务。
4. 专家是否具有不同知识、工具或角色信息，还是同模型、同提示、同材料。
5. 轮数、输出修正、超时、输入长度及实际开销是否具有可比性。

区分两类交付：在原条件下运行作者实现属于复现核对；更换为本平台的模型、材料和引用规则属于移植比较。原模型不可用时记录受限复现条件。结果方向不同也应如实保留。

### 3.3 第二项交付：开发集错误与收益审阅

建议审阅开发集 40—60 道代表题，选择条件和数量先记下来，覆盖以下分组：

| 分组 | 要查的问题 |
| --- | --- |
| 固定流水线对、单智能体错 | 收益是否来自更好的查询、第二跳实体或更多证据 |
| 单智能体对、复杂协作错 | 是否丢失正确候选、过度质疑、无依据改答或被审核弃答 |
| 检索证据充分但答错 | 是证据整合、条件判断、答案格式还是引用问题 |
| 补检索后没有新证据 | 查询是否变化、缺口是否具体、重试为何继续 |
| schema/超时失败 | 失败阶段、业务规则、内部重试及时间预算的关系 |

每题记录初始答案、最终答案、证据变化、改答方向、弃答、失败阶段和开销。人工标注“正确→错误”“错误→正确”用于离线诊断，标准答案不进入运行时控制器。

诊断代码的明确小任务：`protocol_agents.py:147–153` 的五类 Debate 业务校验仍直接抛普通 `ValueError`；`structured_output.py:32` 会将其降为 `$ / invalid_schema`。改为具有错误码和字段位置的 `SchemaViolation`，复用当前日志机制。Lead 已有这类结构，应复用。旧档案未保留的细节仍未知，只在新开发任务验证改进。

### 3.4 第三项交付：一个最小、可证伪的机制

建议候选机制：**围绕证据缺口选择后续动作，并在证据不再增长时停止无效协作。** 这是待验证方法方向，尚未确认新颖性。

可以从固定流水线或现有反馈流水线做独立研究版本：

1. 初次规划、检索、作答后，保留候选答案、引用和未解决的事实缺口。
2. 明确缺哪个事实、条件或实体，再决定改写查询、调用材料互补的专家、请求证据核验或结束。
3. 每次记录查询、证据来源、去重后的新增片段、是否补足缺口、答案变化和开销。
4. 证据已充分时结束；连续无新增证据且缺口未缩小时有界结束，保留不确定性。阈值只在开发集确定。

实现上，`protocols_v2.py` 的条件枚举目前仅覆盖既定审核/重试规则。新控制器先作为单独的研究策略接入运行层，策略配置纳入快照与指纹；如需增加协议阶段或路由条件，使用新的协议语言版本，保留已有 V1/V2 的执行语义。新策略也应沿用现有资源约束和轨迹记录。

运行时信号只能来自可见证据和状态；gold supporting facts 仅用于离线衡量检索效果。新增片段数量不等于有效证据，需同时核查它是否支持缺失事实。单独依靠模型自报置信度不足以定义触发条件。

初版对比保留：强单智能体迭代检索、固定流水线、现有反馈流水线、候选机制。随后做消融：移除定向补证据、移除停止规则，以及把相同动作策略交给单智能体执行。若单智能体执行相同策略能获得同等收益，研究贡献应按检索/控制机制表述，继续寻找协作的必要条件。

### 3.5 公平比较与新评价

- 开销比较：固定模型与输入数据，记录全部实际调用、Token、检索片段及耗时；设置若干预算档位，比较质量—开销曲线。相同每次 `top_k` 或相同最大调用上限，都不代表相同实际开销。
- 机制诊断：另建共享证据包的受控实验，在证据相同时比较答案整合；另建总检索证据预算受控实验检验检索控制。共享证据包不使用 gold 构造，也不按答案成绩选择；此类实验单独说明条件。
- 稳定性：先做约 100 道开发题的小实验；筛选后对有价值的关键条件增加重复运行，检查改进是否稳定，再扩大规模。
- 主指标：HotpotQA 可延续 Answer F1，SP/Joint、弃答、完成率和开销作为补充；提前指定一个主要配对比较，报告差值与区间。
- 重新冻结：已看过的 1,000 题继续用于已有结果与探索分析。新方法的最终评价从剩余候选中核对并排除全部已知曝光后另建清单，或选独立数据集；不能直接按剩余数量声称没有曝光或泄漏。
- 推广范围：有稳定开发收益后，再增加第二模型或独立数据任务。领域演示不能代替通用算法验证。

## 4. 应用线：一个可用、可核验的小场景

### 4.1 领域建议

默认建议先做“**研究生参加国内学术会议的差旅报销流程咨询**”，前提是能拿到本校明确、有效的正式材料和少量真实问题。目标范围包括适用条件、事前审批、所需票据和办理顺序；规则数值均以材料为准。

若导师合作的服装企业能在一周内提供一套可用规则和真实咨询，优先切换到“**某一类服装定制的售前规则咨询**”，限定尺码/面料选项、起订条件、交付规则和所需客户信息。首版输出咨询结论与待确认项。

| 场景 | 适合起步的条件 | 需要额外解决的事 |
| --- | --- | --- |
| 校内会议差旅流程 | 能取得正式制度、办事说明及师生问题 | 文件版本与适用范围；缺失个人条件时追问 |
| 服装定制售前 | 企业能提供固定产品范围、业务规则和问题 | 专有词、规则完整性、企业人员验收 |
| 单病种资料咨询 | 有可靠材料及专业人员参与核验 | 医学答案的专业验证；建议在具备资源时安排 |

选择依据是资料和验收条件。校内示范与企业示范属于一个应用方向的备选，首月集中完成其中一个。

### 4.2 最小领域系统

建议用 2—3 位具有不同材料职责的专家，加一个汇总审核角色。例如差旅场景分别负责审批流程、费用条款、票据与材料要求。**专家分工应对应知识职责，不能只改名称。**

目前单个实例绑定一个材料版本，可把同一职责下的多份 TXT/MD 文件组成一个知识源版本。首版先利用此能力，不急于扩展任意多知识源联合检索。

实现顺序：

1. 收集约 5—10 份核心材料，登记原始地址、发布部门、发布日期、适用范围、当前有效性和导入版本。
2. 建立中文/中英混合文本索引；给新索引单独版本，保留旧英文 HotpotQA tokenizer 和实验语义。同步核查中文查询生成与跨跳实体传递。
3. 首轮人工整理成 TXT/MD，核对表格中的条件与数值。若真实材料主要是可提取文本的 PDF，再安排 PDF/DOCX 解析和页码/段落来源；遇到扫描件才评估 OCR。
4. 先做单知识库基线与固定流水线，再做按材料职责分工的系统，使用相同原始材料并记录配置。
5. 发布领域系统版本，冻结问答清单，通过现有批量评测入口运行，人工核对引用和关键条件。
6. 补充信息时保留已知条件与上下文。现有请求合同只有单个 `question`，首版可在业务界面收集必需条件后形成明确问题；跨轮会话与状态恢复应单独实现并验收。

### 4.3 领域题库与验收

先收集约 50 个候选问题，作为开发与演示材料；同时规划另行保留的验收题，避免把反复调试的演示题当作独立验证。题型至少覆盖：单条规则、跨文件条件组合、办理步骤、缺失条件、材料无答案或版本冲突。

每题人工给出关键事实/步骤、必要条件、可接受表述、支持条款和应答行为。评价建议包括：

- 必要事实、条件和步骤的正确率/覆盖率。
- 引用是否真实定位、是否支持相应结论、材料是否适用。
- 信息不足时能否提出必要追问；资料无答案时是否准确表达不确定。
- 专家或实际办事人员的可用性评价，以及实际调用、耗时和费用记录。

领域评分先以独立人工评分表和离线导出完成，保持旧 HotpotQA 评分不变。需要长期使用时再新增 `scorer_id/scorer_version`、评分规则与评分记录，并扩展报告器和主指标选项。当前平台没有现成的上述领域质量评分能力；LLM 评分若使用，应单独固定评分配置并做人工核验。

异机交付先以单用户演示范围完成。按现有请求耗时选择同步或任务式 API 合同，设置明确超时和失败语义。对外提供服务时补与暴露范围对应的访问控制及调用限制。

### 5.2 通用智能体协作的扩展顺序

导师关于广义 QA 的判断可以作为平台的长期方向。建议在领域问答完成后，用一个具体任务逐步验证：

1. 将领域结论整理为结构化“需求单/材料检查单”，验收字段和缺失信息。
2. 接入只读业务工具，例如读取产品规则或查询任务状态，记录输入输出。
3. 有真实业务需求后，再实现订单写入等动作，并为其设计权限、幂等、失败恢复和必要人工确认。

每一步保留当前问答与实验入口。当前 LangGraph 用于执行流程，知识检索为 BM25；知识图谱只有在明确的实体关系查询需求出现时再评估。

## 8. 参考与后续精读范围

以下来源用于确定核查和比较方向。本次主要核实原始论文页面及摘要，尚未逐项完成论文与作者代码的深度复现审计。

1. [Du et al., Improving Factuality and Reasoning in Language Models through Multiagent Debate, ICML 2024](https://proceedings.mlr.press/v235/du24e.html)；[作者代码](https://github.com/composable-models/llm_multiagent_debate)。用于选择具体协作复现对象。
2. [Trivedi et al., Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions, ACL 2023](https://aclanthology.org/2023.acl-long.557/)；[作者代码](https://github.com/StonyBrookNLP/ircot)。用于选择迭代检索的强单智能体比较方向。
3. [Jeong et al., Adaptive-RAG, NAACL 2024](https://aclanthology.org/2024.naacl-long.389/)。已有工作研究按问题复杂度选择检索策略，因此“按需调用/自适应”本身不足以构成新颖性证明。
4. [Chen et al., When and Why Does Multi-Agent Debate Fail and Does It Really Underperform?](https://arxiv.org/abs/2510.20963)。预印本讨论协作协议导致辩论失效及同预算改进，说明结论应限制于具体条件。
5. [Xu et al., Rethinking the Value of Multi-Agent Workflow: A Strong Single Agent Baseline](https://arxiv.org/abs/2601.12307)。预印本讨论强单智能体模拟同构协作流程；用于提醒后续加入相同策略的单智能体比较，不据此推断本平台结果。
