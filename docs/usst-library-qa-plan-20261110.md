# 上海理工大学图书馆领域问答应用示范（USST Library QA）实施方案

日期：2026-11-10
版本：第 2 版。依同日评审意见修订五处：正式评价的答案要求、多专家执行模式、题库计数、B2 归因表述、口语化验收与评分档位。
状态：**计划，尚未执行**。本文不含已完成的系统、题库、评测或用户验收结果。
定位：应用方向（阶段 6）。不改变研究方向的实验基线、指标口径与已冻结档案。
依据：上海理工大学图书馆官网公开页面（2026-11-10 采集）、本仓库当前代码、两轮方案评审意见。

## 1. 目标与定位

建设一套基于现有可配置多智能体协作平台、以**上海理工大学图书馆公开制度材料**为知识源的领域问答示范系统。

定位表述：

> 基于可配置多智能体协作平台的高校图书馆制度与办事流程智能问答应用示范。

需要强调的能力不是"能聊天"，而是：

1. 答案能定位到**具体文件、版本与原文行号**；
2. 不满足条件时**说明缺什么条件**，而不是给出看似合理的结论；
3. 材料未覆盖或属于个人记录时**明确拒答**，不编造数字；
4. 上述行为可被一套固定题库和人工评分复核。

官网已存在"AI 馆员"与"常见问题"入口。本项目不宣称替代或优于该入口，只作为平台能力的应用示范。

## 3. 平台事实与约束

以下为代码核查结论，规划中的参数以此为准。

### 3.1 知识源导入

位置：`src/knowledge/corpus.py`、`src/knowledge/store.py`、`backend/knowledge_api.py`、前端 `/knowledge`。

| 项目 | 约束 | 依据 |
| --- | --- | --- |
| 格式 | 仅 `.txt` / `.md` | `corpus.py:39-40`，报 `unsupported_format` |
| 编码 | UTF-8（按 `utf-8-sig` 解码） | `corpus.py:44-46`，报 `invalid_encoding` |
| 单文件 | ≤ 2 MiB | `corpus.py:17,41-42` |
| 单次总量 | ≤ 10 MiB | `corpus.py:18` |
| 单版本文件数 | ≤ 10 份 | `corpus.py:16` |
| 片段长度 | ≤ 600 字符 | `corpus.py:15` |
| 片段总数 | ≤ 20,000 | `corpus.py:19` |

一个知识源版本可包含多份文件（上限 10）。因此"多专家各看一部分材料"通过**多个知识源**实现，不需要改检索层。

### 3.2 协议与系统

位置：`src/runtime/protocols_v2.py`、`src/runtime/protocols.py`、`src/runtime/instances.py`、`src/runtime/system_store.py`。

**`single_expert`（系统 A 使用）**

- 槽位只有一个 `expert`，且 `maximum` 必须为 1（`protocols_v2.py:87-89`）。
- 阶段只有一个 `answer`。

结论：系统 A **只能有 1 个实例**，页面上无法再增加独立的 Answer Validator。验证由该专家自身的输出结构与提示词内嵌完成。文档与配置须与此一致，否则会被协议校验拒绝。

**`multi_expert`（系统 B 使用）**

- 槽位固定为 `planner`、`experts`（`maximum=3`）、`reviewer`（`protocols_v2.py:132-136`）。
- 阶段固定为 `plan → propose → review`，且 `propose` 只能出现一次（`protocols_v2.py:90-92`）。
- **执行模式默认是顺序执行。** 阶段字段 `mode` 默认取 `sequential`（`protocols.py:40`），而 `team` 模板的 `propose` 阶段未显式设置 `mode`（`protocols_v2.py:135`）。
- **并行可用，但须显式配置。** `protocols_v2.py:53-54` 只强制 `plan / retrieve / lead / review / answer` 必须串行，`propose` 允许 `parallel`。协议页面提供"并行后汇合"选项，配置即可，无需开发。

结论：三位专家绑定**同一个 `propose` 阶段**的三个实例，v1 明确选择 `parallel`；未选择时按串行执行。`multi_expert` 的语义是"独立专家分别作答、汇合后统一审核"，**不等同于 Lead Agent 按问题动态选择专家**，两者不可混用表述。

**实例字段**

`AgentInstance` 含 `agent_id / agent_type / name / description / model_config{model_name, system_prompt, temperature, max_tokens} / source_id / source_version / top_k`（`src/runtime/instances.py:34-42`）。每个实例绑定**一个**知识源的**一个固定版本**。每套系统 1–5 个实例。

### 3.3 批量评测

位置：`src/evaluation/platform_store.py`、`src/evaluation/platform_datasets.py`、`backend/evaluations_api.py`。

| 项目 | 约束 | 依据 |
| --- | --- | --- |
| 材料模式 | `context_mode` 取 `question_context` 或 `system_sources`，默认前者 | `platform_store.py:75` |
| 内置基线 | `kind='builtin'` 时**必须** `question_context`，否则报「标准基线需要使用问题自带的逐题材料」 | `platform_store.py:294-296` |
| 用户系统 | `kind='system'` + `system_id` + `version` | `platform_store.py:49-58` |
| 主指标 | `Literal['em','f1','sp_em','sp_f1','joint_em','joint_f1']`，默认 `f1` | `platform_store.py:88` |
| 支撑事实类指标 | `sp_*` / `joint_*` 要求 `question_context` 且每题提供 `supporting_facts` | `platform_store.py:285-286` |
| 专家数 | `expert_count` 取值 2–3，默认 2；仅作用于内置基线方法定义 | `platform_store.py:81` |
| 执行方式 | `execution_mode` 取 `sequential` 或 `parallel`，默认串行；仅作用于内置基线，用户系统按其发布协议执行 | `platform_store.py:82` |
| `top_k` | 1–50，默认 3 | `platform_store.py:80` |

本项目的评测配置因此固定为：

- 两个目标均为 `kind='system'`，各指定已发布版本；
- `context_mode='system_sources'`；
- `primary_metric` 只能取 `em` 或 `f1`，且**仅作占位**；
- 题库每题不提供 `context`，也不提供 `supporting_facts`。

**关于 EM/F1 的纪律**：`src/evaluation/metrics.py` 的归一化与空白分词面向英文 HotpotQA。中文制度长答案的 EM/F1 不具解释力，**不得作为领域质量结论**写入任何报告。领域质量一律使用第 7 节的人工评分。

### 3.4 题库格式与实验用途

导入校验位置：`platform_store.py:93-128`。

- 顶层为 JSON 数组，1–10,000 条；
- 必填 `_id`（或 `id`，≤200 字符、唯一）与 `question`（≤2000 字符）；
- `answer` 若提供则必须为非空字符串，填空字符串会报错；
- `type` 为 ≤100 字符的短字符串，可自由填写，用于导出后分组；
- `context` 与 `supporting_facts` 本项目不使用。

**`answer` 能否省略取决于实验用途**（`platform_datasets.py:207-209`）：

| 用途 `purpose` | `answer` 是否必须 | 依据 |
| --- | --- | --- |
| Smoke 测试 | 可省略 | 无该校验 |
| 开发实验 `development` | 可省略 | 无该校验 |
| 正式评价 `evaluation` | **不可省略**，任一题为空即报「正式评价需为每道题提供标准答案。」 | `platform_datasets.py:207-209` |

因此本题库采取统一策略：**每题都写参考答案**，包括无答案题写期望应答文本。这样三档用途均可直接使用正式评价功能，不需要修改代码。该答案仅作评测参考，不改变第 7 节的人工评分口径。

### 3.5 中文检索能力边界

位置：`src/knowledge/bm25_retriever.py`。

- 分词：NFKC + 小写后，提取 `[a-z0-9]+` 词串，并对汉字串追加**单字与二字片段**（前缀 `zh:`），即字级 unigram + bigram，**无词典分词**（`bm25_retriever.py:33-40`）。
- 阈值为 `MIN_SCORE = 0.0`，只保留得分大于 0 的片段，无共有字则返回空（`bm25_retriever.py:45`）。
- 跨跳实体取自引号/书名号内文字、标题命中词、以及带"大学|学院|研究所|公司|中心|委员会|医院|市|县"等后缀的词，最多 3 个（`bm25_retriever.py:161-168`）。

以下情形会召回失败，属**已知识别风险**而非缺陷：

1. 同义改写后与原文无共同汉字（如"能借几本"对"限额"）；
2. 事实被 600 字符切分到不同片段；
3. 中文实体无后缀且未被引号或标题包含。

材料转换须针对第 1 条做规避（表格转完整句式）；题目措辞则**不刻意迁就原文**，见 4.4 与 6.4。

### 4.2 来源记录规范

每份材料头部固定三行，随后为正文：

```
来源：<官方 URL>
采集日期：2026-11-10
页面更新日期：<页面标注的日期；未标注则写"未标注">
```

同时维护一份 `docs/usst-library-qa-sources.md` 来源清单，字段为：文件名、页面标题、URL、发布部门、页面日期、采集日期、适用范围、是否需馆员确认、备注。

原文副本（HTML 另存或纯文本）另行保存，以便核查转换是否改变含义。

"网站仍然显示"不等于"学校当前一定按此执行"。凡涉及入口、收费、时限的条款，须在来源清单标注确认状态。

### 4.3 转换规范

1. **保留全部读者类型**。借阅规则页核心是表格，必须拆成完整句子，例如：

   > 研究生、教工可借中外文图书 30 册，借期 60 天。
   > 本专科生可借中外文图书 30 册，借期 30 天。

   不得压缩为"一般 30 册"，否则"研究生能借几本"会零分召回。

2. **只改表达形式，不改制度含义**。不补充页面未写的数字、入口或流程。
3. **一事实一段**，段间用空行或 `#` 标题分隔，避免同一条件跨段。
4. **单一文件聚焦单一职责**，便于后续按职责拆分为多个知识源。

### 4.4 检索试查验收（不调用模型）

导入后在知识源详情页使用"检索试查"，对每份材料至少用 3 个问句验证：

| 材料 | 试查问句示例 | 期望 |
| --- | --- | --- |
| `01` | 研究生最多能借多少本书、研究生借书期限、寒暑假到期怎么办 | Top-5 含对应条款行 |
| `02` | 被预约的书能续借吗、在哪里办理续借 | 含"被预约图书不能办理续借"所在行 |
| `03` | 书逾期了还能借书吗、逾期影响馆际互借吗 | 含停借与恢复条款 |
| `04` | 馆际互借一次能借几本、国图借的书多久还、取书在哪里 | 含册数、期限、取书地点三行 |

**术语问句与口语问句都要测。** 每个知识点准备一对：

- 官方术语版："研究生图书借阅限额是多少？"
- 口语版："我是硕士生，最多能借几本书？"

术语版用于确认索引与条款覆盖可用；口语版用于确认真实用户措辞下的稳定性。两者结果都记入试查记录。

口语版失败时如实记录为**检索边界**，不得通过修改题目措辞来掩盖，也不因此在阶段 1 引入向量检索。若多份材料的口语版普遍失败，作为阶段 4 的已知限制写入报告，并在阶段 2 观察是否影响可用性。

任一份材料的术语版试查失败，先改材料表述，不要进入下一阶段。该阶段零模型成本。

## 5. 系统配置

### 5.1 系统 A：单专家基线 `usstlib-baseline v1`

| 项目 | 配置 |
| --- | --- |
| 协议 | `single_expert` v1 |
| 实例 | 1 个 `expert`（不可再加实例） |
| 知识源 | 1 个库，含 4 份文件，固定 v1 |
| 模型 | 与系统 B 完全一致 |
| `top_k` | 与系统 B 一致，建议 5 |

### 5.2 系统 B：多专家协作 `usstlib-multi v1`

| 实例 | 角色 | 知识源（固定 v1） | 职责 |
| --- | --- | --- | --- |
| 1 | `planner` | 无 | 拆解问题、识别需查的规则维度 |
| 2 | `expert` | 借阅库（`01`+`02`） | 借阅资格、册数期限、续借条件 |
| 3 | `expert` | 逾期库（`03`） | 逾期后果、停借范围与恢复 |
| 4 | `expert` | 馆际互借库（`04`） | 适用对象、流程、期限费用 |
| 5 | `answer_validator` | 无 | 汇总证据、统一作答、标注不确定 |

| 项目 | 配置 |
| --- | --- |
| 协议 | `multi_expert` v1 |
| 专家阶段 | 三个专家绑定同一 `propose` 阶段 |
| 执行方式 | **显式选择 `parallel`（并行后汇合）**；不选择时为串行 |
| 模型与 `top_k` | 与系统 A 一致 |

### 5.3 可选对照 B2 `usstlib-multi-shared v1`

把系统 B 的三个 `expert` 全部绑定**同一个全库知识源**，其余配置不变。三个系统构成：

| 系统 | 协作方式 | 每位专家可访问的材料 |
| --- | --- | --- |
| A | 单专家 | 全部四份 |
| B2 | 规划 + 三专家 + 审核 | 全部四份 |
| B | 规划 + 三专家 + 审核 | 按职责分别为 2 份 / 1 份 / 1 份 |

两种对比能回答的问题不同：

| 对比 | 保持不变的项 | 可回答的问题 |
| --- | --- | --- |
| A → B2 | 可访问材料相同 | 在材料条件相同时，单专家与多专家协作方案的整体表现差异 |
| B2 → B | 协议、模型、提示词、`top_k`、执行模式相同，仅专家知识源绑定不同 | 材料分工本身是否带来收益 |

**归因纪律**：A 与 B2 的差异除协作结构外，还包含 Planner 与 Reviewer 实例、角色提示词、检索次数和模型调用数的不同。因此不得表述为"仅多智能体结构不同"，只能表述为两套协作方案的整体表现差异。若需分离这些因素，需另做提示词与调用次数的受控实验，不在 v1 范围内。

B2 属于可选增强，**不阻塞 v1 完成**。建议在阶段 3 顺带发布，若时间不足可推迟到阶段 4 之后。

| 条件缺失 | 5 | 我想续借一本书，可以吗 | 指出需确认预约状态、有无逾期、是否已续借 |
| 无答案 | 4 | 我现在借的书具体哪天到期 | 不编造个人记录，指向"我的图书馆"或借还书处 |
| 合计 | 34 | | |

### 6.3 题目字段

每题均提供 `answer`（见 3.4 的用途要求）：

```json
{"_id": "usstlib-dev-001", "question": "我是硕士生，最多能借几本书？", "answer": "研究生、教工可借中外文图书 30 册，借期 60 天。", "type": "事实问答"}
```

无答案题同样写期望应答文本：

```json
{"_id": "usstlib-dev-030", "question": "我现在借的书具体哪天到期？", "answer": "无法通过公开资料查询个人借阅到期日期，需通过图书馆个人借阅系统或一楼借还书处核实。", "type": "无答案"}
```

内部评分表另存完整标注：`gold_key_facts`、`gold_conditions`、`gold_steps`、`gold_citation`（文件名 + 条款/行号）、`expected_behavior`（`answer` / `ask_clarify` / `refuse_personal`）。

题库入库使用**学生真实说法（口语版）**；术语版用于阶段 1 试查，不入库。

### 6.4 出题纪律

1. **续借题不追问读者类型。** 按官网规则，续借只看四件事：是否在到期前、是否被他人预约、本人是否有任一册逾期、是否已续借过（"延长一倍"即一次）。读者类型与本息无关。若系统追问读者类型，应按"条件完整"维度扣分。
2. **无答案题不要用"材料没写但现实中存在"的问题**（如赔偿具体金额），否则会把知识库不全误判为模型会拒答。优先使用个人记录类问题。
3. **入库措辞用真实学生说法**，不照抄官网术语；术语版只在阶段 1 用于检索验收。
4. **每题只考察一个判断点**，跨材料题的判断点明确写成"需同时满足 A 与 B"。
5. **口语失败如实记录**，不改题迁就系统。

## 7. 评分

评分先以人工评分表完成（CSV 或 Markdown 表格均可），**暂不写脚本**。等分组统计明显拖慢推进时，再考虑读取 `results.json` 自动生成待评分表。

### 7.1 四项评分

每项 0/1/2 分，分值含义统一如下：

| 分值 | 含义 |
| --- | --- |
| 2 | 完全满足该维度 |
| 1 | 部分满足，存在非关键遗漏 |
| 0 | 不满足，或出现该维度的关键错误 |

| 维度 | 操作定义 |
| --- | --- |
| 事实正确 | 数字、册数、期限、入口是否与原文一致 |
| 条件完整 | 必要条件是否说全；含无关追问（如续借追问读者类型）扣分 |
| 引用可核验 | 引用片段的 `filename` 与 `line_start–line_end` 区间内确实含支持该结论的原文 |
| 行为正确 | 该作答时作答、该追问时追问、该拒答时拒答 |

流程问答在"事实正确"与"条件完整"之外，另按步骤判定：**步骤齐全且顺序正确**方可给 2；步骤缺失或顺序颠倒最多 1；缺少必要前置条件按关键错误处理，计 0。

引用核对使用现有引用渲染字段：`filename`、`source_version`、`line_start`、`line_end`（见 `src/state.py` 的 `EvidenceChunk`，前端由 `EvidenceLocation.tsx` 展示）。

### 7.2 致命错误与严重不通过

出现任一项即标记为**严重不通过**，该题不计入均分，单独统计：

- 编造政策数字或期限；
- 遗漏关键限制（如漏掉"被预约不能续借"）；
- 给出无原文依据的办理步骤；
- 使用旧版或第三方口径（如英文站旧版册数）。

严重不通过的题不得因其他维度得分高而视为成功；报告须同时给出严重不通过题数与其绝对占比。

### 7.3 记录项

每题记录：系统版本、答案摘要、四项得分、严重不通过标记、模型调用次数、耗时、失败原因（若运行失败）。

调用次数与耗时直接取自评测结果，不另行计算。

## 8. 实施阶段

| 阶段 | 内容 | 交付 | 完成标准 | 模型成本 |
| --- | --- | --- | --- | --- |
| 1 材料 | 确认四份资料，转换 Markdown，记录来源与采集日期，导入并通过检索试查 | 4 份文档 + 来源清单 + 试查记录（含口语版结果） | 每份材料术语版 3 个问句召回对应条款；口语版结果如实记录 | 0 |

| 5 用户验收 | 3–5 位同学用自己的问题试问 | 真实反馈汇总 + 演示案例 | 各有一个答对 / 追问 / 无答案的真实案例 | 少量 |

参考工期：阶段 1 半天，阶段 2 一到两天，阶段 3 一天，阶段 4 一到两天，阶段 5 一天。
